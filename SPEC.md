# Software Specification

**Product:** Employee Support Ticket Management Application

**Author:** Vennela Varadhi

## 1. Project overview

A local web application with a React interface and an Express API. Employees report IT problems. Support staff see every ticket, update status, and comment. Access is enforced on the server from the signed-in user's role.

MongoDB is not installed on this machine, and Docker is not available. The API stores data in a local SQLite file through Node.js 22's built-in `node:sqlite` module. The server is started with `--experimental-sqlite`. No extra database package is required.

## 2. Problem statement

Employees need a simple application to report workplace IT problems and track their resolution. Support staff need a central place to manage and resolve employee requests. The demo uses fictional people and fictional problems dated 18 November 2026.

## 3. User roles

- `employee`: own tickets only.
- `support`: all tickets.

Demo accounts are seeded. There is no self-registration.

| Name | Username | Role |
| --- | --- | --- |
| Ravi | ravi | employee |
| Admin | admin | support |

Passwords are fictional demo values read from environment variables at seed time, hashed with bcrypt, and never written into JavaScript source. `.env` is gitignored. `.env.example` documents the variable names and the same fictional demo values so the practical can be run.

A second fictional employee is created only inside the test database so "cannot view another employee's tickets" can be executed. That person is not part of the demo seed.

## 4. Functional requirements

- Log in and log out. The server returns the current user. Unknown or wrong credentials are rejected.
- An employee creates a ticket with title, description, category, and priority. Status is set to Open. Created By and Created Date are set by the server. The client cannot set status or owner.
- An employee lists and opens only tickets they created. Support staff list and open every ticket.
- List screens support text search on title and description, and filters for category, priority, and status. Search is limited to tickets that role is allowed to see.
- Dashboards show counts of visible tickets by status, plus the ticket table.
- Content update (title, description, category, priority) is allowed for the creating employee and for support staff, and only when status is not Closed.
- Status update is support staff only, including when the ticket is already Closed.
- Comments: the creating employee may comment on their own ticket; support staff may comment on any ticket; empty comments are rejected; comments work when the ticket is Closed. Each comment stores the author name and a server timestamp.
- Ticket details show the fields, status, priority, and the comment list.

## 5. Non-functional requirements

- Beginner-friendly structure and few dependencies.
- Responsive layout from about 360px wide up to a desktop dashboard.
- Professional UI: sidebar, summary cards, ticket table, status badges, priority indicators, filters, create form, details page, and comments.
- Server-side validation for every important action.
- API errors use JSON and appropriate HTTP status codes, without stack traces.
- Sample dates and live timestamps are visibly different.

## 6. Ticket data structure

### Ticket

- `id`: generated by the database.
- `title`: required, trimmed, 1 to 100 characters.
- `description`: required, trimmed. No extra length limit was specified.
- `category`: Hardware, Software, Network, Access, Other.
- `priority`: Low, Medium, High.
- `status`: Open, In Progress, Resolved, Closed. New tickets start as Open.
- `created_by`: user id of the signed-in creator.
- `created_at`: set once by the server.
- `updated_at`: set on create, and updated when content changes, status changes, or a comment is added.
- `timestamp_origin`: `sample` or `system`. This is a display marker so seeded dates are not confused with live clock times. It is not a business rule, and users cannot set it.

### Comment

`id`, `ticket_id`, `author_id`, `body`, `created_at`.

### User

`id`, `name`, `username`, `password_hash`, `role`.

## 7. Business rules

1. Only support staff can change ticket status. This includes a Closed ticket.
2. Employees can see only their own tickets.
3. Support staff can see all tickets.
4. Closed tickets cannot be edited. Editing means title, description, category, and priority. Status changes and comments are separate actions.
5. Comments can still be added to closed tickets.
6. Title and description cannot be empty.
7. Employees can update their own tickets only if they are not closed. Support staff may also update those same content fields when the ticket is not closed.
8. All important actions must be validated on the server side.

Direct consequences used in the API, not extra rules:

- A new ticket's status is Open because an employee cannot set status.
- Category and priority must be one of the listed values because no empty option exists.
- A whitespace-only title or description is empty after trim.

## 8. Acceptance criteria

### Normal cases

- Ravi logs in, creates a valid ticket, and sees it in his list with status Open and his name as creator.
- Ravi sees only his tickets. Admin sees all five sample tickets plus any new ones.
- Admin changes a ticket from Open to In Progress, and from Closed to Open.
- Ravi and Admin update title, description, category, and priority on a ticket that is not Closed.
- Ravi comments on his ticket. Admin comments on any ticket. The comment shows the author name and timestamp.
- A comment can be added to the Closed sample ticket "Request a second monitor".
- Search and category filter return matching visible tickets.
- After a content edit, status change, or comment, `updated_at` changes and `created_at` does not.

### Negative cases

- A wrong password is rejected.
- Ravi receives 403 when requesting another employee's ticket.
- Ravi receives 403 when sending a status change.
- An empty title, a whitespace-only title, an empty description, and a title longer than 100 characters are rejected with 400. The ticket is not stored.
- A content update on a Closed ticket is rejected with 400 for both Ravi and Admin.
- An empty comment is rejected with 400.
- A request with no login cookie receives 401.

### Edge cases

- A title of exactly 100 characters is accepted. A title of 101 characters is rejected.
- A category, priority, or status outside the lists is rejected.
- A non-numeric ticket id receives 400. A numeric id that does not exist receives 404.
- Comments already stored remain visible after the ticket is Closed and after it is reopened.

## 9. Error handling

- 400: validation failure or a content edit on a Closed ticket, with a short message naming the field.
- 401: missing or invalid login.
- 403: authenticated but not allowed (wrong role, or an employee opening or commenting on someone else's ticket).
- 404: ticket id is numeric but missing.
- 500: unexpected errors. The client receives a generic message. Details stay in the server log.

## 10. Security requirements

- Password hashes only. Demo passwords and `JWT_SECRET` come from environment variables.
- The JWT is stored in an httpOnly cookie (`SameSite=Lax`).
- Every ticket and comment route checks the cookie and applies the role rules on the server. Hiding a button is not the control.
- SQL uses bound parameters.
- API responses never include `password_hash`.
- CORS is limited to the Vite origin.

## 11. Project limitations

- One machine, one SQLite file, no MongoDB.
- `node:sqlite` is experimental on Node 22.
- Two demo users only. No sign-up, attachments, notifications, or audit log beyond `updated_at` and comments.
- Sample descriptions are short fictional text because the brief required a description but did not supply one.

## 12. Sample data

Fictional. All five tickets are created by Ravi. `timestamp_origin` is `sample`. `created_at` and `updated_at` are both `2026-11-18T09:00:00.000Z`. The interface shows that date as 18 November 2026 (sample). Tickets created in the running app use the real server time and `timestamp_origin` `system`, labelled as application time.

1. **Laptop not charging.** Hardware, High, Open. Description: The laptop battery does not charge when the power adapter is connected.
2. **Cannot log in to VPN.** Network, High, In Progress. Description: VPN authentication fails and the employee cannot reach the office network.
3. **Need access to the shared project folder.** Access, Medium, Open. Description: The employee needs permission to open the shared project folder.
4. **Excel keeps crashing on startup.** Software, Medium, Resolved. Description: Microsoft Excel closes immediately after it is opened.
5. **Request a second monitor.** Hardware, Low, Closed. Description: The employee is requesting an additional monitor for their desk.

No sample comments. The database file `server/data/support.db` is gitignored and created by the seed script.
